# Decisions

Append-only. Never rewrite an existing decision; append a superseding one.

Format: `YYYY-MM-DD - <decision, stated as a fact, one sentence> - <why/trigger> (decision #N, plan: <section>)`

- 2026-10-20 - The package is published as `@edgesweden/consent` from the public repository `EdgeSweden/consent` under the MIT licence - set in the plan (decision #1, plan: What this is)
- 2026-10-20 - The default cookie name is `consent` - set in the plan (decision #2, plan: What this is)
- 2026-10-20 - The default layout is blocking with a dimmed backdrop - set in the plan (decision #3, plan: Config)
- 2026-10-20 - Astro is the only framework integration in v1; any other host uses `mount()` directly - set in the plan (decision #4, plan: Out of scope for v0.x)
- 2026-10-20 - Work is delivered in review-gated packages tracked in `docs/progress.md`; an independent review is required before merge and verification evidence lives in the pull request, not in a separate log - keeps the review requirement without extra documents to maintain (decision #5)
- 2026-10-20 - Commits follow Conventional Commits; `main` has a linear history of squash-merged pull requests; releases are tags `vX.Y.Z` - readable history for a public repository and a mechanical link between commit type, semver bump and CHANGELOG (decision #6, plan: Releases)
- 2026-10-20 - `zod` ^4 is a regular dependency, imported only by `./astro` and `validateConfig` - the plan's schema-first validation needs it; approved for P1.1 (decision #7, plan: Validation, Repository layout)
- 2026-10-20 - Config colours are validated against a supported subset (hex, `rgb()`/`rgba()`, `hsl()`/`hsla()`, named colours, `transparent`); any other value fails validation - build-time contrast needs sRGB values without a browser or a colour dependency (decision #8, plan: Validation)
- 2026-10-20 - The default colour tokens are a TypeScript constant that the stylesheet must match; contrast is checked on config colours merged over the defaults, a translucent colour in a checked pair is a "cannot check" warning, and the custom property of colour token `fooBar` is `--consent-foo-bar` - the contrast rule needs defaults before the stylesheet exists (decision #9, plan: Validation, Config)
- 2026-10-20 - `validateConfig(input)` returns `{ ok, config?, errors, warnings }` with every error as `{ path, message }`, collects all errors rather than stopping at the first, and is exported from `./astro` - keeps zod out of the browser entry without a new export (decision #10, plan: Validation)
- 2026-10-20 - `cookie.maxAgeDays` is an integer 1–400, `cookie.name` an RFC 6265 token, `cookie.path` starts with `/`, `cookie.domain` is a hostname, `theme.zIndex` an integer, locale keys are non-empty, and `width`, `radius`, `font` and `vars` values are non-empty strings - the plan left these fields unconstrained (decision #11, plan: Validation)
- 2026-10-20 - A locale link `href` is a root-relative path, an absolute `http(s)` URL or a `#fragment`; anything else fails - keeps `javascript:` and `data:` links out of the banner (decision #12, plan: Validation)
- 2026-10-20 - The maintainer starts every review and re-review in a separate session; an implementer never launches or messages a reviewer, and an implementer-initiated review does not count - keeps the review independent of the implementing session (decision #13)
- 2026-10-20 - `locale`, service ids, service cookie names, link ids and link labels are non-empty strings - an empty link label leaves an unnamed link and an empty id cannot be referenced; maintainer delegated the call (decision #14, plan: Validation)
- 2026-10-20 - A stored consent cookie is valid only when `v` is `1`, `p` is a string, `t` a finite number and `c` an object of booleans, otherwise it is treated as absent; when several cookies share the name the first in `document.cookie` is read, and a required category stored as `false` is reported granted without making the cookie stale - the plan said only "unparseable is absent"; approved for P1.2 (decision #15, plan: Cookie, Required categories)
- 2026-10-20 - `consent:change` is dispatched only on a change, never at mount; the `data-consent-<id>` attributes carry the initial state - a mount-time event would look like a choice to a DOM consumer; approved for P1.2 (decision #16, plan: State API)
- 2026-10-20 - Before mount, `getConsent()` returns `null` and `withdraw()` is a no-op - there is no config to act on; approved for P1.2 (decision #17, plan: State API)
- 2026-10-20 - Consent state is a module singleton: `mount` returns `void`, and a second call is a no-op whichever document it is given - one state per page backs the document-free state API; approved for P1.2 (decision #18, plan: Mount)
- 2026-10-20 - The settings dialog is always modal (`aria-modal`, focus trap, siblings `inert`, centred) with the `layout.backdrop` backdrop; Escape or its close control closes it, a backdrop click does nothing, and closing it returns to the banner when the banner opened it - the plan did not say whether the dialog follows `layout.blocking`; approved for P1.3 (decision #19, plan: Accessibility)
- 2026-10-20 - On open, focus moves to the dialog container (`tabindex="-1"`), never to a button, including the non-blocking banner at load; on close it returns to the element focused at open when that is still connected, otherwise to the body - keeps Accept all and Reject all on an equal footing; approved for P1.3 (decision #20, plan: Accessibility, Principles)
- 2026-10-20 - Blocking `inert` is applied to the other children of `body`, and an element that was already `inert` keeps it on close; there is no scroll lock - `inert` already blocks interaction and a scroll lock would be another style mutation on the host page; approved for P1.3 (decision #21, plan: Accessibility)
- 2026-10-20 - The settings dialog shows one native checkbox per category, set from the current state, required ones checked, disabled and labelled `alwaysActive`, with services listed by name and description and no cookie names; its buttons are Accept all, Reject all and Save with equal styling, and `buttons.order` applies only to the first layer - the plan named the controls but not their layout; approved for P1.3 (decision #22, plan: Choice)
- 2026-10-20 - `openSettings()` before mount is a no-op, and a click on `[data-consent="open"]` calls `preventDefault` and opens the settings dialog - consistent with decision #17, and lets a link serve as the reopen control; approved for P1.3 (decision #23, plan: State API)
- 2026-10-20 - When `body` does not exist at mount the dialogs are built on `DOMContentLoaded` while the state is established immediately - mount may run from the head; approved for P1.3 (decision #24, plan: Mount)
- 2026-10-20 - Class names carry the `consent-` prefix and are not a public contract in 0.x; the `--consent-*` custom properties are - leaves the markup free to change while the theme surface stays stable; approved for P1.3 (decision #25, plan: Repository layout)
- 2026-10-20 - `mount` and `openSettings` stay off the public entry until the record hook (P1.5) and link tokens (P1.4) are in place; the banner is tested through its internal modules until then - a public `mount` would silently ignore a configured `record` and render `{link:<id>}` literally; resolves P1.3 review finding 1 (decision #26, plan: Record, Locale resolution)
- 2026-10-20 - The default `layout.position` is `center` - fits the blocking, dimmed default of decision #3; approved after P1.3 review (decision #27, plan: Config)
- 2026-10-20 - Escape on a non-blocking banner acts as its close control (nothing stored) when focus is inside the banner, and is ignored otherwise - matches the close control's "decide later" meaning without taking Escape from the host page; approved after P1.3 review (decision #28, plan: Principles, Accessibility)
- 2026-10-20 - The stylesheet ships in the package and is bundled and served by each site from its own build (the Astro integration imports it in P1.6; other hosts import `@edgesweden/consent/styles.css`); the core never fetches or injects it, nothing is loaded from a third party, per-site styling goes through the config `theme`, and `dist/styles.css` is minified by the build - supersedes the plan's "imported by the core bundle" and "CSS copied"; a runtime `<link>` would be a request before a choice (decision #29, plan: No visual flash, Repository layout, Principles)
- 2026-10-20 - A `{link:<id>}` token in `description` or `settingsDescription` renders as `<a class="consent-link" href>` with the link's label as text and no `target` or `rel`, so it opens in the same tab; tokens in other strings stay text - the plan said only that tokens become `<a>` elements; approved for P1.4 (decision #30, plan: Locale resolution)
- 2026-10-20 - At runtime a token whose link id is missing stays literal text, and a link whose `href` fails decision #12 renders its label as plain text; the core applies the same href rule as validation from a zod-free module - covers a config passed to `mount` without `validateConfig`; approved for P1.4 (decision #31, plan: Locale resolution, Validation)
- 2026-10-20 - The theme is applied to `.consent-root` with `style.setProperty` before the root joins the document: `colors.<token>` → its colour property, `radius.box|button|control` → `--consent-radius-*`, `font` → `--consent-font`, `zIndex` → `--consent-z-index`, `layout.width` → `--consent-width`; `vars` are applied first so a named key wins, and at runtime a `vars` key that is not `--consent-*` or names a colour token is skipped - the plan named the values but not their properties or precedence; approved for P1.4 (decision #32, plan: Config, CSP)
- 2026-10-20 - `record` runs after the cookie write, the `consent:change` event and the subscribers of each written choice (including `withdraw()`), in the order the choices were made; a function recorder gets its own copy and a throw or rejection is swallowed; the URL form re-checks the URL with the validation rule, posts the record as a JSON string (`text/plain;charset=UTF-8`, no preflight) through `sendBeacon` and falls back to `fetch` with `method: "POST"`, `keepalive: true` and default credentials when `sendBeacon` is missing, returns `false` or throws; `packageVersion` is injected at build time from `package.json`; `mount` and `openSettings` join the public entry - the plan named the transports but not the encoding, ordering or fallback triggers; approved for P1.5 (decision #33, plan: Record, Choice, State API)
- 2026-10-20 - The size budget of `.` (core incl. stylesheet) is 7 KB gzipped, counting every file the entry loads - with the record hook the self-contained core measured 5.99 KB, leaving no room for P1.6–P1.8; supersedes the 6 KB in the plan; maintainer decision after P1.5 review (decision #34, plan: Size budget, Principles)
- 2026-10-20 - `astro` is an optional peer dependency (`>= 5`) and a `^5` devDependency - the plan sets the peer range; maintainer approved adding it for P1.6 (decision #35, plan: Repository layout, Astro integration)
- 2026-10-20 - The integration takes `config` as a required path, resolved against the Astro root unless absolute, to a module whose default export is the config; it loads the module with the `runnerImport` of the Vite that Astro resolves, watches the module and everything it imports, re-exports the module through `virtual:@edgesweden/consent/config` rather than serialising it so a `record` function reaches the browser, and imports the stylesheet through a `page-ssr` injected script because Astro drops CSS imported from a `page` script - the plan did not say how a TypeScript config is loaded or how the stylesheet is included; maintainer chose Vite loading for P1.6 (decision #36, plan: Astro integration, No visual flash)
- 2026-10-20 - The `astro` peer range is `>= 5.4`, the integration resolves Astro and its Vite from the site's root, and a real build is tested at Astro 5.4.0 with Vite 6.2.0 through the `astro-min` devDependency alias - decision #36's `runnerImport` needs Vite >= 6.1, which Astro 5.0–5.3 do not require; supersedes the `>= 5` range of decision #35 and the plan; maintainer decision after P1.6 review (decision #37, plan: Repository layout, Astro integration)
- 2026-10-20 - `release.yml` runs on `v*.*.*` tags, calls `ci.yml` as a reusable workflow (which no longer runs on tag pushes), refuses to publish unless the tagged commit is on `main`, the tag equals the `package.json` version and `CHANGELOG.md` has a non-empty `## [X.Y.Z] - YYYY-MM-DD` section (`scripts/release-check.js`), then upgrades npm to 11 inside the job and runs `npm publish --provenance --access public` - the plan did not say how the CI job is reused or what counts as an entry, and trusted publishing needs npm >= 11.5.1 while Node 22 ships npm 10; approved for P1.8 (decision #38, plan: Releases, CI)
- 2026-10-20 - The package name is claimed once by the maintainer with a hand-published, immediately deprecated `0.0.0` placeholder so that a trusted publisher can be attached, after which publishing is restricted to the workflow; this is the only publish from a machine - npm attaches a trusted publisher only to an existing package; maintainer decision for P1.8 (decision #39, plan: Releases)
- 2026-10-20 - A release pull request sets the `package.json` version and moves `Unreleased` under the version's heading; the maintainer tags its squash-merge commit - `main` takes only squash-merged pull requests, so the bump cannot happen at tag time; approved for P1.8 (decision #40, plan: Releases)
- 2026-10-21 - `release.yml` stages each release with `npm stage publish --provenance --access public` on npm `^11.15.0`, the trusted publisher may only stage (direct `npm publish` and `dist-tag` are not allowed), and a version goes live only when a maintainer approves it with 2FA on npmjs.com or with `npm stage approve` - a stolen GitHub login or token could otherwise push a tag that publishes straight to every site using the package; supersedes the `npm publish` and npm 11 parts of decision #38; maintainer decision before v0.1.0 (decision #41, plan: Releases)
- 2026-10-21 - The `./gate` and `./gtag` entries import the core as the external package self-reference `@edgesweden/consent`, never bundled, so they share the page's one consent state (decision #18); their size budgets count only their own code, and the zero-dependency lint rule allows that one specifier - with `splitting: false` a relative import would give each entry its own state that never sees a choice; approved for P2.1 (decision #42, plan: Adapters, Size budget, Repository layout)
- 2026-10-21 - `./gate` exports `installScriptGating(config, doc = document)`, which returns a disposer that only unsubscribes; calling it always installs, and `gateScripts` only tells the Astro integration whether to import it - the plan named both `install` and `installScriptGating` and did not say whether the function reads the flag; approved for P2.1 (decision #43, plan: Adapters, Script gating)
- 2026-10-21 - A gated script is activated by replacing it with a new `<script>` that has every attribute except `type`, `data-consent-type` and `nonce`, the original's text and its `nonce` property; `data-consent-type`, when present, becomes the live script's `type` (e.g. `module`), and a script with `src` gets `async = false` unless it had `async`, so activated scripts run in document order - the plan said "same attributes" without the `type`, nonce or ordering rules; approved for P2.1 (decision #44, plan: Script gating, CSP)
- 2026-10-21 - Gating scans the document on every consent state it receives (including mount) and once more on `DOMContentLoaded` when installed while the document is loading; only scripts whose `data-consent` names a granted category are activated, so an unknown id never runs, scripts added later wait for the next change, and a script that has run stays loaded after a withdrawal - the plan said only "on each grant"; approved for P2.1 (decision #45, plan: Script gating)
- 2026-10-21 - Activated scripts run one at a time in document order: an external classic or a module script without `async` holds every later activation until its `load` or `error` event, as in parsed HTML; a queued script is activated only if its category is still granted and it is still in the document when its turn comes, and a script is queued once across changes and installations - `async = false` alone ordered external scripts but let a following inline script run first; resolves P2.1 review finding 1 and refines decision #44's ordering (decision #46, plan: Script gating)
- 2026-10-21 - The activation queue is kept in document order after every scan, so a newly granted script runs before a later one already waiting, and only a script the browser loads holds it: one without `async` whose `type` is `module` (untrimmed, any case) or, with `src`, empty or a JavaScript MIME type essence from the HTML standard - appending to the queue ran later scripts first, and matching any type containing "script" stalled the queue on `text/typescript`; resolves P2.1 re-review findings 1 and 2 and refines decision #46 (decision #47, plan: Script gating)
- 2026-10-21 - Each `consentMode.mapping` key is a declared category id with a non-empty list of Consent Mode v2 keys (`ad_storage`, `ad_user_data`, `ad_personalization`, `analytics_storage`, `functionality_storage`, `personalization_storage`, `security_storage`), `extra` takes the same keys, any other key fails, and `wait_for_update`, `region`, `ads_data_redaction` and `url_passthrough` are not supported - the plan named neither the key set nor what a mapping key may name; approved for P2.2 (decision #48, plan: Config, Validation, Google Consent Mode v2)
- 2026-10-21 - The Consent Mode adapter sets only the keys listed in `mapping` and `extra`; a key neither lists is never sent, and the README tells sites to list every key their tags read - denying unlisted keys would set values the site did not configure; approved for P2.2 (decision #49, plan: Google Consent Mode v2)
- 2026-10-21 - `./gtag` exports `installConsentMode(config, win = window)`: it pushes `default` synchronously on install, then `update` with every mapped key whenever the mapped values differ from the last ones pushed (so at mount only for a stored choice that grants something, and never for a change to unmapped categories), never re-sends `extra`, pushes each command onto `window.dataLayer` (created when missing) as an `arguments` object without defining `window.gtag`, does nothing without `consentMode` or on a window it already installed on, and returns a disposer that only unsubscribes - gtag.js ignores array entries, and the plan did not settle mount-time updates, repeats or the signature; approved for P2.2 (decision #50, plan: Adapters, Google Consent Mode v2)
- 2026-10-21 - When both adapters are enabled, the Astro integration calls `installConsentMode(config)` before `installScriptGating(config)` after `mount(config)`, so the default consent command is queued before a required gated tag can execute - the plan required both installs after mount but did not settle their relative order; approved for P2.3 (decision #51, plan: Astro integration, Google Consent Mode v2)
- 2026-10-21 - An external classic script with `nomodule` does not hold the activation queue, while a `module` script still does regardless of whether it has `nomodule` - module-aware browsers skip a classic `nomodule` script without a load or error event, which stalled every later gated script in 0.2.0; resolves the v0.2.0 final review P2 and refines decision #47 (decision #52, plan: Script gating)
